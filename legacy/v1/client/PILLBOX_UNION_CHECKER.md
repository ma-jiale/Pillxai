# 药盒统一校验器（PillBox Union Checker）设计

目标：把「机载扫码 / 平板摄像头 / RFID」三条识别路径合并成**一个**药盒校验器。
任何一条路径可用即可走完整流程；缺失的路径对使用者完全不可见；界面文案不出现任何技术名词。

---

## 1. 现状为什么需要合并

| 位置 | 现状 | 后果 |
| --- | --- | --- |
| `UIManager.cs:1044` `BeginIdentificationSession` | 无条件 `scanner.StartScanner(...)` | 没有平板摄像头的机器，开仓即报「摄像头暂不可用」 |
| `UIManager.cs:1330` `ResetIdentificationAfterRemoval` | 每次重置都重新开摄像头 | 错误提示反复覆盖「放入药盘」 |
| `UIManager.cs:1781` | `usesRfid = Source == Rfid` | 机载条码识别的药盒被当成「条码盒」，关仓前仍强制走平板摄像头 |
| `UIManager.cs:3017-3029` | 条码分支 `WaitForNoBarcodeAsync` | 无摄像头立即失败 → 「轨道保持打开」→ 重试死循环 |
| 文案 | 「摄像头检测失败」「仍可使用机器扫码或 RFID」 | 把实现细节暴露给使用者 |

结论：**识别已统一，可用性与取盒检测没有统一**。统一校验器就是补这两块。

## 2. 结构

```
              ┌───────────────────────────────┐
  RFID ──────▶│                               │
  机载扫码 ──▶│   PillBoxUnionChecker         │──▶ Verified(patientId)
  平板摄像头 ▶│   （唯一的状态机与判定）       │──▶ FeedbackChanged(中性文案)
              └───────────────────────────────┘──▶ Diagnostic(仅日志/调试面板)
                            ▲
                   Tick() 由 UIManager.Update 驱动
```

三层，各自职责单一：

- **通道层** `IPillBoxChannel`（`Assets/Scripts/Hardware/PillBox/PillBoxChannels.cs`）
  只回答「我能不能用 / 我看到有没有盒 / 我看到是谁的盒」。硬件细节（串口事件、`WebCamTexture`、RFID 映射）全部封在通道内。
- **判定层** `PillBoxUnionChecker`（`PillBoxUnionChecker.cs`）
  纯 C#，无 `UnityEngine` 依赖，时钟可注入，因此可脱离 Unity 做单测。
- **文案层** `PillBoxFeedbackText`（`PillBoxFeedbackText.cs`）
  枚举 → 一句话。所有面向使用者的字符串只从这里出。

三个通道实现：

| 通道 | 可用条件 | 在位来源 | 身份来源 |
| --- | --- | --- | --- |
| `RfidPillBoxChannel` | `dispenser.IsConnected` | `IsRfidCardPresent` | UID → 名册映射 |
| `DispenserBarcodePillBoxChannel` | `dispenser.IsConnected` | `IsBarcodePresent`（APPEARED/DISAPPEARED 边沿） | 条码 → `ParsePatientIdFromBarcode` |
| `TabletCameraPillBoxChannel` | `WebCamTexture.devices.Length > 0`（5 秒缓存探测） | 「最近 3 秒内解码成功」，会话期间每秒自动重开 | 同上 |

## 3. 联合语义（设计核心）

| 判定 | 规则 | 理由 |
| --- | --- | --- |
| **可用性** | 任一通道可用 → 校验器可用；**0 通道才算阻塞** | 一台机器只需要一种识别方式 |
| **身份** | 保留每个通道的结论；跨通道出现两个不同患者 → 撤销信任，不选边 | 冲突时选边等于替使用者做决定 |
| **身份（单通道换盒）** | 同一通道报出不同患者 → 只撤销确认状态并更新该通道结论，保留其他通道证据再重新判定 | 换盒不需要中间态 |
| **正则化** | 统一 `PillBoxId.SameId`：忽略大小写，`000010` 与 `10` 视为同一患者 | 机载条码补零，名册可能不补零 |
| **在位** | 任一通道说在位 → 在位（乐观） | 误判「不在位」会提前关仓，夹坏药盒 |
| **已取出** | 只有**本会话中真正见过盒子**的通道仍可用、全部明确报告离位，并稳定 `1.5s` → 才算取出 | 边沿事件会丢；沉默不能当作证据 |
| **无正向观测** | `confirmedPresence` 为空时永不自动关仓，等超时后转人工确认 | 宁可不关，不可夹盒 |
| **超时** | 默认 120s；超时返回 `false` + 「请确认药盒是否已完全取出」 | 取代原来的重试死循环 |

关键安全细节：`DispenserController.ClearRfidStateWithoutEvent()` 会在 `OPEN_TRAY` 前清空条码状态，
而 STM32 只在**出现/消失的瞬间**各报一次。因此关仓判断必须「先见到一次 APPEARED」，
否则「当前没有条码」这个状态既可能是「已取出」也可能是「从未看到」。

## 4. 状态机

```
StartSession ──▶ AwaitingBox ──(身份一致)──▶ Ready ──(使用者确认)──▶ AwaitingRemoval ──(通道全清 + 稳定)──▶ Cleared
                    │                          │                          │
                    ├─(身份不符)──▶ Rejected ◀─┘                          └─(超时)──▶ Rejected
                    └─(无可用通道)──▶ Blocked ──(通道恢复)──▶ AwaitingBox
```

- `Rejected` 只在「盒还在」时停留，盒子离开后自动回 `AwaitingBox`。
- `Blocked` 只在 0 通道时出现，恢复后自动继续，不需要使用者重启。
- 平板通道是**一次性解码器**（`HandleDecode` 解码后自动 `StopScanner`），所以它在会话期间每秒自我重开；
  其它两个通道 `Poll()` 为空实现。

## 5. 文案层（不暴露技术）

禁用词：摄像头 / 扫描 / 扫码 / 条码 / 二维码 / RFID / 串口 / 蓝牙 / 传感器 / 机载 / 硬件 / 相机。
`PillBoxFeedbackText.IsNeutral()` 提供校验，`AssertAllNeutral()` 可在编辑器启动时自检。

| 场景 | 旧文案 | 新文案 |
| --- | --- | --- |
| 等待放入 | 请将药盒放入分药机，系统将通过机载扫码、摄像头或 RFID 自动识别 | 请将药盒放入舱内 |
| 核验通过 | 已通过条码确认药盒信息 | 药盒已确认，请核对处方 |
| 患者不符 | 药盒与所选患者不匹配 | 该药盒与当前长者不符，请取出 |
| 双源冲突 | 条码与 RFID 指向不同患者，请取出药盒后重新识别 | 药盒信息不一致，请取出后重新放入 |
| 未登记 | RFID：xxx 该药盒的 RFID 尚未绑定患者 | 无法确认该药盒，请取出后重新放入 |
| 取盒提示 | 请取出二维码/条形码药盒，摄像头确认药盒离开后轨道将自动收回 | 请取出药盒 |
| 取盒失败 | 摄像头检测失败，轨道保持打开。请检查摄像头后按确认键重试 | 请确认药盒是否已完全取出（+ 手动「已取出」按钮） |
| 无可用通道 | 摄像头暂不可用，仍可使用机器扫码或 RFID 识别药盒 | 设备未就绪，请联系维护人员 |

技术人员需要的细节仍完整保留在 `EZLog` 与 `Diagnostic` 事件里（含通道名、原始码、患者映射结果）。

## 6. UIManager 接线（已实现，待编译与实机验证）

- 普通识别、自动识别和 Scan 页面创建统一 checker；Update 在键盘快捷键提前返回之前调用 Tick，各平台均驱动计时。
- Verified 复用处方准备流程；异步返回后校验会话结果与当前 Ready 身份，冲突或取出后不再显示过期确认。
- 取消和完成后统一调用 WaitForRemovalAsync(120)，失败时显示“已取出”人工确认按钮。按钮确认后才发送关仓；关仓失败保留页面供重试。
- 完成流程先释放药片计数摄像头，再创建新的取盒会话。机器若已经开仓则不重复开仓；会话读取当前在位状态。建立会话前就已取走且没有正向观测的盒子，按规则转人工确认。
- 会话结束解除硬件事件订阅并停止平板识别；设备失联、场景销毁同时结束自动等待与人工确认等待。
- 确认框复用现有按钮，无需新增场景绑定。平板曾参与识别时，不能以读码超时确认离位，需等待超时后人工确认。
- 原 RFID 稳定时间字段用于统一离位稳定窗口，最低 1.5 秒。三个通道的配置开关尚未接入 AppConfig，本次按已有能力自动可用。
